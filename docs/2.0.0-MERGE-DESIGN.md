## 0. 為什麼是 2.0.0（不是 1.0.7）

顯示架構整條換掉：FrontBoard 懸浮場景 → backboard 托管的獨立 root 守護進程。
這不是加法功能，是使用者路徑上的顯示層替換（舊路徑移除、無 fallback 開關，
見 §6），且新二進位、新 entitlements、新設置區段一次到位。按 semver 慣例升 major。
build 號 28 → 29 連續，不跳號。

## 1. 架構總覽

```
主 App（com.ycwl.Lyrics，mobile 用戶，UIApplicationMain + scenes）
  │ 寫快照（唯一寫方）
  │ App Group group.com.hailong.TrollLyricsDesk / key lyric.snapshot
  │ 設置頁 Enable／Disable daemon（§5）
  ▼
HUD daemon（helper 可執行檔 TLDHUDDaemon，見 §2）
  │ 只讀快照（1 秒定時器讀一次，轉成藥丸顯示；不寫快照、不碰網路、不碰 MediaRemote）
  │ root + launchd KeepAlive；backboard 托管窗口，一次註冊、永不重建
  ▼
SpringBoard backboard/window server（SBSAccessibilityWindowHostingController
  registerWindowWithContextID:atLevel:，level 10000010.0）
```

- 主 App 繼續做它本來就做的事：MediaRemote 跟隨、LRCLIB 查詞、逐歌偏移、
  「·」修復、寫快照、應用內歌詞、小組件、激活。daemon 不接播放引擎。
- daemon 只做一件事：把快照顯示成桌面藥丸。鎖屏時只藏視圖、停定時器；
  解鎖時只取消隱藏、重啟定時器；窗口與進程都不動——所以沒有「恢復」這件事。
- 觸摸：v1 不做（HUD-Test 同款決定）。藥丸 `_ignoresHitTest = YES`，永不吞觸摸。
  TrollSpeed 的 HID 管線（`HUDMainApplication.mm` 的 UIEventDispatcher／
  `TSEventFetcher.mm`）不移植。
- Jetsam：不抄 `JetsamHelper.h` 的 `BypassJetsamByProcess`——它在 TrollSpeed
  裡零調用，是死代碼（ARCHITECTURE_ANALYSIS §7 claim 5）。存活靠 launchd
  KeepAlive + root。
- XExternalHUD：零複製（無許可證）。只作機制對照，代碼一行不取。

## 2. Daemon 如何進正式版：獨立 helper 可執行檔

### 2.1 放置

- 新 target `TLDHUDDaemon`，product type `com.apple.product-type.tool`，
  產物為 Mach-O 可執行檔 `TLDHUDDaemon`（thin arm64，MinOS 15.0）。
- 嵌進 App 包內根目錄：`TrollLyricsDesk.app/TLDHUDDaemon`
  （與 `TrollLyricsDesk` 主二進位並列，不進 `PlugIns/`、不進 `Frameworks/`——
  它不是 extension 也不是動態庫，進那兩個目錄會被系統當插件／庫掃描）。
- App target 依賴 daemon target（`PBXTargetDependency`），scheme 的
  BuildActionEntries 加 daemon 一項（`buildForArchiving = YES`），
  archive 時 daemon 一定先編好。
- 拷貝用 App target 的 Run Script phase「Embed HUD Daemon」，不用
  Copy Files phase（`dstSubfolderSpec` 的枚舉值易錯、難審）：
  `cp -f "$BUILT_PRODUCTS_DIR/TLDHUDDaemon" "$TARGET_BUILD_DIR/$FULL_PRODUCT_NAME/TLDHUDDaemon"`，
  拷完 `test -f` 斷言在位，否則 build 響亮失敗。
- daemon 的 dSYM：daemon target 繼承工程級 `DEBUG_INFORMATION_FORMAT =
  dwarf-with-dsym`（Release），archive 的 `dSYMs/` 應含
  `TLDHUDDaemon.dSYM`；驗包時三個 dSYM 的 UUID 逐一對二進位（見 §8）。
  若 archive 實測缺 daemon dSYM，build.yml 補 `dsymutil` 顯式生成——
  這是已知風險點（§9），不預先寫死。

### 2.3 HUDLyricsSnapshot 移植核實（對 `LyricStore.swift` @ `c5c2c27`）

逐函數對過，結論：邏輯可原樣移植，只改類名前綴。

- 分隔符表：Swift `LyricStore.swift:180` 與 `:221`
  `[" — ", " – ", " - ", " · ", "—", "–"]`＝ObjC `HUDSnapshotSeparators`
  一字不差；順序即優先順序。
- `stableSongIdentity`（Swift `:296-300`）：title／artist 任一帶分隔符即取該
  字段，否則 title。ObjC `HUDStableSongIdentity` 同款。
- `searchTerms`（Swift `:311-328`）：只拆 `" · "`，字段順序 `[artist, title]`，
  頭＝真歌名、尾＝真歌手。ObjC `HUDSearchTerms` 同款——**build 28 的「·」
  修復在 daemon 側同樣成立**。
- `lyricLocation`（Swift `:254-294`）：ObjC `HUDLyricLocationFor` 同款；
  差異一處且是故意的：daemon 側 `lyricTexts` 傳空集合——無行快照的 fallback
  分支本來就沒有行表可建（有行時根本不走 `lyricLocation`），空集合時
  Swift 原邏輯同樣落到「artist ≥8 字純中文短句」兜底，行為一致。
- `currentElapsed`（Swift `:134-150`）＋逐歌偏移（`:152-171`）：
  playing 時 `elapsedWhenPaused + (now - startedAt)`、暫停時
  `elapsedWhenPaused`，再加該歌 `lyric.timeOffset|<identity>`；ObjC 同款，
  `elapsed < 0` 夾到 0（Swift playing 分支有 `max(0, …)`，等效）。
- 快照字段：`lyric.snapshot`（`LyricStore.dataKey`）、`lyric.noMusic`
  （`noMusicKey`）、`startedAt` 為 JSONEncoder 預設的自 2001 秒數——三處
  皆與 Swift 一致。daemon 只讀，永不寫快照。

### 2.4 新增：daemon 響應強制測試文字

主工程設置頁的「強制懸浮測試文字」開關（`LyricStore.isTestTextEnabled`，
key `floatingLyric.testTextEnabled`）在 1.0.6 是給 FrontBoard 窗的；
FrontBoard 停用後，若 daemon 不讀它，開關會變成只影響應用內歌詞區，
使用者會以為開關壞了。daemon 側在 `TLDHUDLyricsSnapshot` 讀快照前先讀
該 flag：為真時顯示 `懸浮測試 · 桌面歌詞 2.0.0 · HH:mm:ss`
（格式同 `LyricStore.testText()`，版本號取 daemon 常量 `kTLDHUDVersion =
@"2.0.0"`）。這是本次移植唯一的功能性加法，其餘皆為搬運。

## 3. 關鍵細節：plist 的 ProgramArguments[0] 必須是 helper 路徑

### 3.1 陷阱（已對源碼核實）

HUD-Test 的 `InstallDaemonPlist`（`HUDTest/main.mm:28-62`）寫 plist 時用
`HUDExecutablePath()`（`HUDPaths.mm`，`_NSGetExecutablePath()`）當
`ProgramArguments[0]`。在 HUD-Test 裡這是對的：那是一個二進位兩種模式，
`-install-daemon` 跑在同一個二進位裡，`_NSGetExecutablePath()` 就是 daemon
自己。

主工程是兩個二進位。**主 App 若直接調用同款寫法，拿到的是主 App 自己的
路徑**（`…/TrollLyricsDesk.app/TrollLyricsDesk`），plist 會指向主 App
二進位加 `-hud`——主 App 二進位沒有 `-hud` 分支（`Overlay/main.m` 無條件
`UIApplicationMain`），launchd 拉起它等於再開一個主 App，daemon 永遠起不來，
且 `launchctl load` 仍 exit 0（0.2.0 stale-plist 事故同款靜默失敗）。

### 3.2 實作方式（本文檔定死）

- `InstallDaemonPlist` **只留在 helper 二進位內**（`HUD/TLDHUDDaemonMain.mm`），
  主 App 側沒有任何寫 plist 的代碼。helper 進程內 `_NSGetExecutablePath()`
  就是 helper 自己，`ProgramArguments[0]` 天然正確。
- 主 App 側 Enable 的流程是：spawn **helper**（root）跑 `-install-daemon`，
  再 `launchctl load`。spawn 目標路徑由新增函數算出，不用
  `_NSGetExecutablePath()` 的原值：

```objc
// HUD/TLDHUDPaths.h —— TLDHUDHelperExecutablePath()
// 規則：取當前進程可執行檔所在目錄 + "/TLDHUDDaemon"；
// 若當前進程本身就是 TLDHUDDaemon，則返回自身路徑。
//   主 App：…/TrollLyricsDesk.app/TrollLyricsDesk
//        → …/TrollLyricsDesk.app/TLDHUDDaemon  ✓
//   helper：…/TrollLyricsDesk.app/TLDHUDDaemon → 自身  ✓
// 不用 NSBundle（tool 二進位無 bundle，mainBundle 路徑不可靠），
// 不寫死 TrollStore 安裝路徑（容器 UUID 每次重裝都可能變）。
NSString *TLDHUDHelperExecutablePath(void);
```

- `TLDHUDHelper.mm` 內所有 spawn 目標（`IsHUDEnabled` 的 `-check`、
  `SetHUDEnabled` 的 `-install-daemon`／`-exit`／直接 `-hud` fallback）
  一律用 `TLDHUDHelperExecutablePath()`，**不用 `HUDExecutablePath()`**。
  `HUDExecutablePath()` 只保留給 helper 進程內的 `InstallDaemonPlist`
  與 daemon 自身的日誌行。
- 模板 `HUD/TLDHUDDaemon.plist` 裡的 `ProgramArguments[0]` 是佔位符
  （`/var/jb/Applications/TrollLyricsDesk.app/TLDHUDDaemon` 風格的示例路徑），
  安裝時一定被重寫；自檢斷言模板含佔位符且安裝代碼含重寫邏輯，兩者缺一不可。

## 4. 關鍵教訓：Enable 必須一律重寫 daemon plist

保留 HUD-Test 0.2.1 的寫法（`HUDHelper.mm` 的 `SetHUDEnabled(YES)`，
commit `cb66edb`），一字不改其語義：

- 0.2.0 事故：Enable 只在 plist 缺失時才安裝。TrollStore 重裝後容器 UUID
  變了，舊 plist 的 `ProgramArguments[0]` 指向已不存在的二進位；
  `launchctl load` exit 0，進程永遠起不來，狀態頁卻顯示「已啟用」。
- 0.2.1 修法：每次 Enable 都先讀舊 plist 記下舊 `ProgramArguments[0]`
  （日誌行 `main: daemon plist ProgramArguments[0] old=… new=…`），
  再以 root 重跑 `-install-daemon` 重寫；寫完先 best-effort `launchctl
  unload`（清掉 launchd 手裡的舊 job，rc 記日誌、不阻塞），再 `load`；
  load 後等 3 秒、`IsHUDEnabled()` 複核，跑起來記
  `main: daemon started after launchctl load (3s check)`，沒起來記
  `main: daemon did not start after launchctl load (3s check)`。
  重寫是冪等的：同一路徑進、同一 plist 出。
- Disable 不動：先等 0.25 秒淡出，再 `launchctl unload`（無 plist／無
  launchctl 時 fallback `-exit`）。

## 6. FrontBoard 懸浮場景：從使用者路徑移除

### 6.1 移除什麼（觸發點全停）

`Overlay/TLDSAppDelegate.m`（`didFinishLaunching` 內）：

- 三處 `startFloatingOverlay` 調用（trollstore／livecontainer／unknown 分支）
  全部不再執行；`TLDSInstallNativeWindowFix()` 也不再調用。
- 兩處 Darwin 鎖屏監聽（`com.apple.springboard.lockstate`／
  `com.apple.springboard.lockcomplete` → `TLDSLockStateChanged`）不再註冊——
  解鎖輪詢（16 次，0.15–4.0s）與 `unlockRestoreFloatingOverlay` 無觸發源。
- 前台復核監聽（`UIApplicationDidBecomeActiveNotification`／
  `UIApplicationWillEnterForegroundNotification` →
  `tlds_reactivateFromForegroundNotification`）不再註冊。
- 2 秒看門狗 `visibilityWatchdog`（→ `tlds_watchdogReactivate`）不再創建。
- 6 秒兜底復核 dispatch（`verifyFloatingVisibility`）不再排程。
- `Overlay/TLDSSceneDelegate.m`：懸浮分支加守衛——即使系統遞來一個
  `TLDSFloatingLyric*` 會話，也只記一行「2.0.0 FrontBoard 懸浮場景已停用，
  忽略」，不建 `TLDSPassThroughWindow`。主界面分支不動。

實作手法：`TLDSAppDelegate.m` 頂部加常量
`static const BOOL TLDSFrontBoardOverlayDisabled = YES;`（2.0.0），
`startFloatingOverlay`／`reactivateFloatingOverlayWithTrigger:`／
`unlockRestoreFloatingOverlay`／`foregroundVerifyFloatingWindow`／
`verifyFloatingVisibility` 各在入口處 early-return（記一行
`診斷2.0.0 FrontBoard 已停用` 日誌）；`didFinishLaunching` 內的觸發點
註冊改為 `if (!TLDSFrontBoardOverlayDisabled)` 包裹。
**代碼留著、不刪**：`createFloatingSceneWithIdentifier:`、
`rebuildFloatingOverlay`、`startFloatingOverlayRecreate`、
`TLDSPassThroughWindow`、`FloatingLyricViewController` 全數保留在 git
歷史與源碼裡，只是不再被調用。刪除會丟掉三代修法的證據與回滾路徑。

啟動分支的新行為（`didFinishLaunching`）：

| installEnv | runMode | displayCapability | 備註 |

### 6.2 為什麼不再留開關 fallback

1. **三代修法共用同一個已證偽的假設**——「後台進程發出的 foreground
   設置／取消隱藏能讓系統重新合成場景」。build 25 後台重建（15:04:30 跑了，
   無窗）、build 26 前台復核（只回前台才回來）、build 27 後台重現
   （16:13:04 跑了，無窗），三次真機全滅（ARCHITECTURE_ANALYSIS §2(d)）。
   build 27 連「重現前台建好的舊場景」都失敗，失敗點在「後台進程＋
   FrontBoard 合成」這個組合本身，不在恢復代碼的細節。
2. **死因已定位到進程形態**：build 27 的 `.ips`（2026-11-27 16:13:05，
   `hidden_files/crash-1.0.6-build27-20261127-161305.ips`）是 FrontBoard
   在解鎖瞬間因後台 insecure drawing SIGKILL 殺進程——不是 jetsam、
   不是代碼閃退。留開關等於留一個「解鎖時可能被系統殺掉」的路徑給使用者
   自己踩。
3. **維護成本**：開關意味著兩套顯示棧（FrontBoard 場景＋daemon）並存，
   每次快照格式、測試文字、鎖屏語義改動都要測兩遍；2.0.0 的驗收矩陣
   （RUN_2.0.0.md）已經是兩倍（daemon 路徑＋LC 應用內路徑），再加第三條
   路徑不可持續。
4. 回滾路徑在 git，不在 UI：真要回頭，`git checkout v1.0.6-lc` 就有完整
   的 FrontBoard 實現；分支紀錄與 `RUN_1.0.6.md` §十三–§十七全數保留。

## 7. 簽名：zsign 如何簽 helper 二進位

`build.yml` 現只簽 App＋Widget（各按自己的 entitlements 簽各的二進位，
整包一起簽會把 App 的 entitlements 套到 Widget 上——同理 daemon 必須
單獨簽）。補一步（在 Widget 簽名之後、打包 IPA 之前）：

```yaml
zsign -a -f -e HUD/TLDHUDDaemon.entitlements "$APP/TLDHUDDaemon"
codesign -d --entitlements - "$APP/TLDHUDDaemon"
```

- `-a` 臨時簽名（無證書）、`-f` 不用緩存、路徑是包內 helper 實體路徑，
  與 App／Widget 同款。
- `TLDHUDDaemon.entitlements` 是自有文件（§2.2）：以 HUD-Test 0.2.0／0.2.1
  真機驗證過的集合為底，只改 `application-identifier` 為
  `com.ycwl.Lyrics`。daemon 不需要 MediaRemote 權限（不讀播放器），
  不需要 `hid.*`（不做觸摸），不需要 `springboard.statusbarstyleoverrides`／
  `allow-background-haptics`（那是主 App 的）。
- build.yml 同步改：IPA／dSYM 檔名 `桌面歌詞-2.0.0.ipa`／
  `桌面歌詞-2.0.0-dSYM.zip`、artifact 名同款；archive layout 驗證加
  `test -f "$APP/TLDHUDDaemon"` 與 `ls dSYMs/`（預期 3 個 dSYM）；
  簽名後三段 `codesign -d --entitlements -` 全數印出，供驗包比對。

## 9. 已知限制與風險（寫在前面，不藏）

1. daemon dSYM 是否進 archive：tool target 的 dSYM 收集未在主工程驗過；
   若 CI 的 `dSYMs/` 只有 2 個，build.yml 補 `dsymutil` 顯式生成再打包。
2. rootless 路徑：plist 裝到 `<jbroot>/Library/LaunchDaemons/`，jbroot
   為 `/var/jb`（存在時）否則 `""`（rootful）；PID／log 在 `/var/mobile/`
   下（真實路徑，不加 `/var/jb` 前綴）——HUD-Test 同款，0.2.1 已驗。
3. 無 launchctl 時 fallback 直接 root spawn `-hud`（無 KeepAlive，死了
   不自動拉起，直到下次 Enable）——HUD-Test 同款，日誌明寫。
4. SpringBoard 重啟後 daemon 自殺等 launchd 拉起（HUD-Test 同款，
   `SBSpringBoardDidLaunchNotification`）；重啟瞬間藥丸會消失數秒。
5. daemon 的歌詞刷新是 1 秒輪詢快照，不是推送；切歌／跟行延遲 ≤1 秒＋
   快照寫入延遲，與 HUD-Test 0.2.0 實測一致。
6. 主 App 被卸載時 daemon 自清（`LaunchServices.ApplicationsChanged`
   監聽，bundle ID 改 `com.ycwl.Lyrics`）；TrollStore IPA 無 `.deb`
   prerm，這是唯一清理路徑。
7. 2.0.0 的真機驗收以 Lee 的設備為準（RUN_2.0.0.md 清單）；紙面驗包
   通過 ≠ 真機通過（1.0.6 的教訓）。
